# D16 final verification plan, pre-registered (November 2026)

**Status: pre-registered on 4 Nov 2026, before any run on the final code.**
- **Owner decisions (4 Nov 2026):**
  - acceptance criterion option 2 with **600 probes per class per run**, pooled confidence intervals, fixed Rules A–E (`acceptance-criterion.md`);
  - the 20-probe pre-flight smoke test, with the frozen connection rule below;
  - every result is published, including invalid and inconclusive ones.
- **Nothing here may change after the first run without a new owner decision.** The decision code is `scripts/d16/stats.mjs` (`PLAN`, pinned by `tests/unit/d16-stats.test.ts`) and `scripts/d16/pooled.mjs`.
- **The runs start only after** the tooling PR containing this plan is reviewed and merged.

## 1. Code under test
- `main` at the commit that merges the tooling PR. It contains PRs #13, #16, #17, #18, #19 and #20 and the Finding 3 fix (`isKnown()` does the same lookup for every address).
- All runs use the same commit, from a clean checkout. `meta.json` records `commit` and `worktreeClean`; a different commit or a modified checkout makes the result NOT_PER_PLAN.

## 2. Environment
- **Machine:** a 4-core cloud sandbox. The CPU model is recorded in `meta.json`; when this plan was written it was an Intel Xeon @ 2.80 GHz. Node 22.
- **Database:** a dedicated scratch MariaDB **11.8.9** container, `nltag-d16-db`, bound to **127.0.0.1:3307** only. Database `nltag_d16`, collation `utf8mb4_uca1400_ai_ci`.
- **Checkout:** no `.env`, `.env.local`, `.env.production` or `.env.production.local` (`run.sh` refuses to start otherwise).
- **Process pinning, as in the historical runs:** P1 (`next start`, production build) on cores 0–1; P2 (load generator) on cores 2–3; P3 (probes) on core 3. The database container is not pinned. `D16_STRESS=0`, ramp 10 s.
- **Isolation:** loopback only, fictional `@nltag.test` addresses, a random `harness-only` secret per run, and a local SMTP sink without STARTTLS, so no mail can leave. Production, Hostinger and real addresses are never touched.

## 3. Address classes
All four classes are probed in every round, in an order that rotates each round.

| Class | Name in `probes.csv` | Shape |
|---|---|---|
| U | `unknown` | no account, not on the allowlist; a fresh address every probe |
| K | `known` | an account with a password, **not** on the allowlist (10 accounts) |
| L0 | `listed` | on the allowlist, no account (2 addresses) |
| L2 | `listedAccount` | on the allowlist **with** an account and password (10 accounts): the shape of every production staff account |

Before each K, L0 or L2 probe, P3 clears that address's own sign-in key and every `class:K:*` window in the scratch database, so every probe is a wrong-password check answered `401`.

**4.1 Pre-flight smoke test.** 20 probes per class at 256 connections. It is published but **excluded from the verdict**.

```bash
D16_N=20 D16_CONNECTIONS=256 scripts/d16/run.sh smoke-1
```

- **Frozen connection rule:** if smoke-1's median P1 CPU (`summary.json` → `cpu.median`) is **≥ 95 %**, the connection count is **256**.
- **Otherwise,** run one more smoke test at 512 connections (`D16_N=20 D16_CONNECTIONS=512 scripts/d16/run.sh smoke-2`). If smoke-2 reaches ≥ 95 %, the connection count is **512**.
- **If smoke-2 is also below 95 %,** stop, report, and wait for an owner decision. No runs are made.
- **The chosen value is frozen for all three runs.** `pooled.mjs` refuses runs with different connection counts.

**4.2 Three runs.** 600 probes per class (2,400 probes per run), each with a fresh P1 process and fresh rate-limit tables. Leave at least 10 minutes between runs.

```bash
D16_N=600 D16_CONNECTIONS=<frozen> scripts/d16/run.sh run-1
```

```bash
D16_N=600 D16_CONNECTIONS=<frozen> scripts/d16/run.sh run-2
```

```bash
D16_N=600 D16_CONNECTIONS=<frozen> scripts/d16/run.sh run-3
```

- **Invalid runs:** a run is invalid if any probe was not `401`, if P1 was not saturated, if the sandbox restarted during it, or if a harness process failed.
  - An invalid run is published as it is and replaced by the next number (`run-4`, then `run-5`).
  - The verdict uses the first three **valid** runs.
  - After two replacements, stop and report.
- **Session:** the runs are driven from an active session. This sandbox has restarted while idle, and a restart during a run makes that run invalid.

**4.3 Analysis.**

```bash
node scripts/d16/pooled.mjs "$D16_OUT_ROOT/run-1" "$D16_OUT_ROOT/run-2" "$D16_OUT_ROOT/run-3"
```

`run.sh` already writes each run's `summary.json` with the former per-run criterion (`analyze.mjs`). That is kept and copied into `pooled-summary.json` **for information only**.

## 5. Decision rules
These are fixed in `scripts/d16/stats.mjs` → `PLAN`.

**Statistic:** the Hodges–Lehmann shift of log(ms) between two classes, shown as a percentage. It is computed for each run, then averaged over the three runs (equal weights). Confidence intervals come from a round-block bootstrap stratified by run, with **2,000 resamples** and seed **20261104**, so the result is deterministic.

| Rule | Applies to | Pass when |
|---|---|---|
| **A** validity | each run | every probe `401`; P1 median 1-s CPU in the probe window ≥ 95 % of one core |
| **B** equivalence | L2–U (primary), K–U, L0–U, L2–L0 | the pooled 90 % CI lies inside ±5 % |
| **C** not slower | L2–U | the pooled one-sided 95 % upper bound is below +2.5 % |
| **D** tail | L2–U | the pooled 90 % CI of the p90 ratio lies inside ±5 % |
| **E** consistency | L2–U | no single run's 95 % CI lies entirely outside ±5 % |

**Verdicts:**
- **PASS:** all rules pass.
- **FAIL:** an estimate lies outside its margin, an interval lies entirely outside it, or Rule E fails.
- **INCONCLUSIVE:** an interval straddles its margin while the estimate is inside. More runs or a decision are for the owner.
- **INVALID:** a run fails Rule A.
- **NOT_PER_PLAN:** the run count, class set, probes per class, commit, connection count or a clean checkout differ from this plan.

`pooled.mjs` exits with 0, 1, 2, 3 or 4 respectively. **D16 is met only by PASS.**

## 6. Expected power and duration
- **Power:** from the historical runs' noise (`criterion-evidence.mjs`), at 600 probes per class per run, the chance that a correct implementation passes is:
  - Rule B: about 1.00 for each comparison;
  - Rule C: about 0.93;
  - Rule D: about 0.97;
  - all rules together: about **0.90**.

  The noise on this sandbox may differ; that is what INCONCLUSIVE is for.
- **Duration:**

  | Step | Time |
  |---|---|
  | Build | about 2 minutes |
  | Each smoke test | about 3 minutes |
  | Each run | about 42 minutes: about 40 minutes of probing (2,400 probes at roughly 1 s under saturation), plus migrate, seed, warm-up and ramp |
  | Pooled analysis | about 10 seconds |
  | **Total, with two 10-minute gaps** | **about 2½ hours** |

- **Table growth:** the flood creates about 14,000 rate-limit rows a minute, and the purge removes at most 5,000 a minute, so `rate_limit_bucket` grows during a run (several hundred thousand rows by its end). Every class is probed in rotation through the same growth, so it does not favour one class. Each run starts with empty tables.

## 7. Outputs and publication
- **Where:** `docs/reports/d16-timing/2026-11-main-<sha>/`, containing:
  - every smoke and run folder (`probes.csv`, `cpu.csv`, `load.json`, `smtp.json`, `meta.json`, `summary.json`), including invalid ones;
  - `pooled-summary.json`;
  - a README with the verdict and anything that did not go to plan.
- **How:** published in a PR for owner review, whatever the verdict. P1's log stays local (git-ignored).

## 8. What a PASS does and does not show
- **It shows** that under one saturating load shape, on this sandbox, a wrong password for an allowlisted account, a non-allowlisted account and an allowlisted address without an account are answered within the agreed margins of an address without an account.
- **It does not show** behaviour on Hostinger's hardware or behind its CDN, or under other load shapes.
- **Out of scope:** the password-reset request path (a separate production-readiness item).
